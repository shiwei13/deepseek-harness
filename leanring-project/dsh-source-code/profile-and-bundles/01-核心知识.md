# Profile、Bundle 与配置层：核心知识

这份文档把三个实验真正需要留下的结论放在一起。重点不是记住文件名，而是理解四个对象、三个位置和一条配置组装链。

## 1. 为什么要引入 Bundle 和 Profile

`dsh` 的实际能力来自插件。模型、工具、Session、沙箱、HTTP 服务和命令行运行器都是插件，但一个产品通常需要同时挂载很多插件，并为每个插件提供配置。

如果 Web、Headless 和其他产品各自维护一份完整配置，那么模型、工具、持久化、沙箱等公共配置会被反复复制。公共配置一旦调整，所有产品配置都要同步修改。

Bundle 用来解决“如何复用和分发一组配置”的问题。它是一份可安装、可复用的插件装配层，可以插入或修改若干 Cordis 配置项。

Profile 用来解决“用户这次到底选择哪些层、按什么顺序组装、在哪里保存自己的修改”的问题。它是一套具名的、用户拥有的运行组合。

因此二者的职责不同：Bundle 是能力或产品的可复用装配层，Profile 是用户最终选择的组装方案。

## 2. 四个概念之间的关系

### 2.1 Plugin：真正执行工作的代码

插件提供实际运行能力。一个插件通常导出 `apply(ctx, config)`，被 Cordis Loader 挂载后才开始工作。

### 2.2 Cordis 配置项：最小的配置单位

最小配置单位既不是整个 Profile，也不是插件 npm 包，而是一条 Cordis 配置项。它表示“挂载一个插件实例”，通常包含稳定的 `id`、插件 `name` 和传给插件的 `config`。

```yaml
- id: learning-observer
  name: ./index.js
  config:
    source: bundle-base
```

同一个插件可以用不同 `id` 挂载多次，每次获得不同配置。因此更准确的说法是：配置项对应一次插件挂载，而插件是被挂载的代码。

### 2.3 Bundle：可复用的配置层

组合包的完整英文是 **composition bundle**，代码和日常讨论通常简称 **bundle**。

Bundle 在自己的 `package.json` 中用 `dsh.bundle.patch` 指向一份 patch 文件：

```json
{
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
```

这个声明只是在说“本 Bundle 的 patch 文件在哪里”。真正插入或修改配置项的是 YAML 文件里的 patch；仅有这个字段不会自动启用 Bundle。

### 2.4 Profile：具名的最终组装选择

Profile 的 `package.json` 直接记录的是按顺序应用的 Bundle 包名，不是插件名：

```json
{
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app"
      ]
    }
  }
}
```

插件通常由这些 Bundle 的 patch 间接选中；Profile 自己的 `cordis.patch.yml` 也可以直接插入一条插件配置项。

整体关系如下：

```text
Profile
└── 按顺序列出多个 Bundle
    └── 每个 Bundle 指向一份 patch 列表
        └── patch 插入或修改 Cordis 配置项
            └── 每条配置项挂载一个插件实例
```

一句话记忆：插件是代码，配置项是一次挂载，Bundle 是可复用配置层，Profile 是用户选择的具名组合，Patch 是修改配置项的操作。

## 3. 三个位置及其所有权

学习时可以说“有三个位置”，但文件系统上更准确的说法是：有两个根，其中 Profile 是 Harness home 的子目录。

```text
dsh 安装的依赖树/                       # 发行版拥有
├── @deepseek-ai/dsh                    # CLI
├── @deepseek-ai/dsh-base               # 官方 Bundle
├── @deepseek-ai/dsh-web-app            # 官方 Bundle
├── @deepseek-ai/dsh-headless           # 官方 Bundle
└── 官方插件包……

~/.dsh/                                 # 用户拥有的 Harness home
├── cordis.patch.yml                     # Home patch，作用于所有 Profile
└── profiles/
    ├── web/                             # 一个具体 Profile
    │   ├── package.json                 # Bundle 顺序和外部依赖
    │   ├── cordis.patch.yml             # Profile patch，只作用于 web
    │   └── node_modules/                # 此 Profile 的外部 Bundle/插件
    └── headless/
        └── ……
```

`~/.dsh` 只是默认值；设置 `DSH_HOME` 后，Harness home 会变成指定目录。

### 3.1 dsh 安装的依赖树

这里不是一个名称固定的目录，而是当前 `@deepseek-ai/dsh` 所在的 Node 依赖树。它的物理路径取决于 npm、pnpm、全局安装、本地安装或源码工作区。

它不只包含 Bundle，还包含 CLI、官方插件和运行库。官方 Bundle 放在这里，是为了与当前 CLI 版本一起发布和升级，并共享同一套 Cordis 与服务定义依赖。

在本仓库源码中，三个官方 Bundle 的源码分别位于 [`packages/bundle/base`](../../../packages/bundle/base)、[`packages/bundle/web-app`](../../../packages/bundle/web-app) 和 [`packages/bundle/headless`](../../../packages/bundle/headless)。本地 pnpm 工作区会把它们链接到 `apps/cli/node_modules/@deepseek-ai/` 下。

### 3.2 Harness home 根目录

Harness home 保存用户拥有的全局状态。根目录的 `cordis.patch.yml` 是 Home patch，对这个 home 里的所有 Profile 生效。

### 3.3 Profile 目录

每个 `$DSH_HOME/profiles/<name>` 都是一套独立的用户组装。它保存 Bundle 顺序、Profile 自己的 patch，以及这个 Profile 单独安装的外部 Bundle 或插件。

官方 Bundle 与用户安装的 Bundle 不放在同一处，是因为它们的所有者和生命周期不同：官方包跟随 dsh 版本升级，用户包按 Profile 选择并应在 dsh 升级后继续保留。若全部装进 dsh 程序目录，不同 Profile 会互相污染，用户还可能需要修改受保护的安装目录；若把官方包复制到每个 Profile，则会造成重复、版本漂移和多份核心运行库。

解析一个 Bundle 时，dsh 先从当前 dsh 安装查找，再从具体 Profile 查找。因此 Profile 中同名的包不能偷偷遮蔽官方内置包，而外部 Bundle 仍可以只安装给需要它的 Profile。实现见 [`resolveBundleDir()`](../../../packages/boot/app-boot/src/profile.ts)。

## 4. Config、Patch 与层级的关系

最终配置不是从某一份完整 YAML 直接读取的，而是从空配置项列表开始，按下面的顺序逐层应用 patch：

```text
空配置项列表
  ↓
Profile 列出的 Bundle patch（按声明顺序）
  ↓
$DSH_HOME/profiles/<name>/cordis.patch.yml
  ↓
$DSH_HOME/cordis.patch.yml
  ↓
启动参数中的 --patch overlay（按参数顺序）
  ↓
最终 Cordis 配置树
```

“后面的层优先级更高”不等于“最后一层替换整棵树”。Patch 通常按 `id` 找到某一条配置项；没有被这一层命中的其他 `id` 会继续保留。

例如 Base Bundle 创建了 `agent`、`web-server` 和 `telemetry` 三条配置项，Profile patch 只修改 `web-server`，Home patch 只修改 `telemetry`，命令行 overlay 只修改 `agent`。最终树会同时包含三个 id，只是每个 id 的最终内容来自最后一次命中它的 patch。

更准确的规则是：对每个配置项及其被 patch 的字段，最后一次写入生效。

### 4.1 `config` 是整值替换，不是深度合并

当某个 patch 为同一 `id` 提供新的 `config` 时，它替换原来的整个 `config` 对象，不会递归保留旧对象里未出现的字段。

```yaml
# 较低层
- id: agent
  config:
    model: deepseek-chat
    temperature: 0.7
```

```yaml
# 较高层
- id: agent
  config:
    temperature: 0.2
```

最终 `agent.config` 只有 `temperature: 0.2`，不会自动保留 `model`。如果高层仍需要 `model`，就要在新的 `config` 中完整写出。

### 4.2 `dsh.bundle.patch` 不是用户 patch

`dsh.bundle.patch` 是 Bundle 作者放在 `package.json` 里的元数据，用来声明该 Bundle 自带 patch 的路径。用户当然可以制作自己的 Bundle 并用同样字段声明其 patch，但日常个人覆盖通常直接写 Profile patch 或 Home patch，不需要把每次改动都包装成 Bundle。

选择方法可以简单记成：只改一个 Profile，用 Profile patch；所有 Profile 都要改，用 Home patch；需要安装、复用或分发给别人，用自定义 Bundle；只想给一次启动临时加层，用 `--patch`。

## 5. 为什么热更新要重新组合多层

启动完成后，dsh 监听两份用户可长期编辑的文件：当前 Profile 的 `cordis.patch.yml` 和 Harness home 根目录的 `cordis.patch.yml`。

Profile patch 只影响当前具名 Profile，Home patch 会影响同一个 Harness home 下的全部 Profile。二者都是独立的可变输入，所以不能只监听“优先级最高的那一层”。

`--patch` overlay 在启动时读取，之后作为固定的顶层参与每次重组，但它本身不被热监听。

当 Profile patch 或 Home patch 改变时，dsh 会从 Bundle 层开始重新组合完整配置，而不是在当前结果上继续修改。这样删除高层 patch 后，较低层原本被遮住的值才能重新显现，也不会留下旧配置残渣。对应代码位于 [`apps/cli/src/profile-boot.ts`](../../../apps/cli/src/profile-boot.ts)。

## 6. Web 与 Headless Profile

仓库内置的 Profile 模板定义在 [`PROFILE_TEMPLATES`](../../../packages/boot/app-boot/src/profile.ts)。首次运行不存在的 `web` 或 `headless` Profile 时，dsh 会在 Harness home 中生成它的 `package.json` 和空的 Profile patch。

```text
web      = @deepseek-ai/dsh-base + @deepseek-ai/dsh-web-app
headless = @deepseek-ai/dsh-base + @deepseek-ai/dsh-headless
```

`dsh-web-app` 在公共基础能力上增加 HTTP/API/浏览器前端，适合持续运行的 Web 应用。

`dsh-headless` 增加一次性任务运行器，不启动面向人的 Web、图形或 TUI 界面。当前实现通过命令行接收任务、运行、输出结果并退出，所以它是一个 CLI 运行方式；但 CLI 与 Headless 不是同义词，因为 CLI 也可以用来启动 Web 服务，而 Headless 描述的是“没有持续的人机界面”。

## 7. 三个实验的最终结论

### 实验一：层如何覆盖

[`01-layer-order/run.ts`](../../profile-demos/01-layer-order/run.ts) 证明 `composeEntries()` 从空列表开始按顺序应用各层，同一 `id` 后写者生效，并且 `config` 是整个对象替换。

这个教学 demo 的每一层都只使用 `learning-observer` 一个 id，所以看起来像“最后一层覆盖全部配置”。真实配置树有很多 id，较高层一般只写少数目标，因此未命中的条目都会保留。

### 实验二：Profile 如何找到 Bundle

[`02-profile-resolution/run.ts`](../../profile-demos/02-profile-resolution/run.ts) 证明 `loadProfile()` 先读 Profile 的 `dsh.profile.bundles`，再按顺序解析每个 Bundle 的 `package.json` 和 `dsh.bundle.patch`。

Bundle 有两个解析位置：当前 dsh 安装优先，具体 Profile 次之。`dependencies` 决定包管理器安装什么，`dsh.profile.bundles` 决定 dsh 实际应用哪些 Bundle 以及应用顺序；二者不是一回事。

`loadProfile()` 此时只加载和解析配置层，不执行插件。

### 实验三：最终配置如何变成运行中的插件

[`03-real-dsh/run.ts`](../../profile-demos/03-real-dsh/run.ts) 走真实 CLI 启动路径。`--dump-config` 只组合并打印最终配置和来源，不挂载插件；正常启动则把同样的配置项交给 Cordis Loader，Loader 根据 `name` 导入插件，并调用 `apply(ctx, finalConfig)`。

实验三使用的是教学用 `dsh-learning-base`，不是官方 `@deepseek-ai/dsh-base`，所以它只启动观察插件，不会启动真实的 Agent、模型或 Web 服务。

## 8. 最小检查命令

查看当前机器上 `web` Profile 实际组装出的配置树：

```sh
dsh --profile web --dump-config
```

运行这三个教学 demo：

```sh
node --import tsx/esm leanring-project/profile-demos/run-all.ts
```

读输出时不要只问“最后一层是谁”，而要逐个 `id` 问：“最后一次修改这个 id 的是哪一层？”
