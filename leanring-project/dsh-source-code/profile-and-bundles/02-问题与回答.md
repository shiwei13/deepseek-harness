# Profile、Bundle 与配置层：问题与回答

这份文档保留学习过程中真正容易混淆的问题。先读完 [`01-核心知识.md`](01-核心知识.md)，再用这里快速复习。

## 1. 配置重复时，配置的单位是 Profile 还是 Plugin？

都不准确。最小配置单位是一条 **Cordis 配置项**，它通常表示一次插件挂载，包含稳定 `id`、插件 `name` 和传给该实例的 `config`。

Plugin 是代码，配置项是“如何挂载这段代码”，Bundle 是复用和分发多条配置项的单位，Profile 是选择和排列多个 Bundle 的最终组装单位。

## 2. Profile 记录的是 Plugin 吗？

不是。Profile 的 `dsh.profile.bundles` 直接记录按顺序应用的 Bundle 包名。

Bundle 的 patch 再插入或修改插件配置项，因此 Profile 通常是间接选择 Plugin。Profile 自己的 `cordis.patch.yml` 也可以直接插入插件配置项，但这不改变 `dsh.profile.bundles` 记录 Bundle 的事实。

## 3. Bundle 到底是什么？英文是什么？

Bundle 是“可安装、可复用的插件装配配方”，内容是一层 Cordis patch。完整英文是 **composition bundle**，源码和日常讨论一般直接说 **bundle**。

它不是已经运行的插件树，也不是某个 Profile 的别名。只有被 Profile 列出并在启动时应用后，它的配置才进入最终树。

## 4. `dsh.bundle.patch` 是不是用来覆盖配置文件？

它声明的是“这个 Bundle 的 patch YAML 在哪里”，例如：

```json
{
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
```

覆盖动作来自 YAML 中按 `id` 编写的 patch，而不是 `package.json` 字段本身。这个 Bundle 还必须出现在某个 Profile 的 `dsh.profile.bundles` 中，才会参与组装。

你可以制作自己的 Bundle，并用 `dsh.bundle.patch` 声明它的 patch。只是个人配置通常直接写 `$DSH_HOME/profiles/<name>/cordis.patch.yml`；需要复用、安装或分发时，才值得制作 Bundle。

注意这里是 **patch**，表示配置补丁；不是 **path**。`dsh.bundle.patch` 的值恰好是一条文件路径。

## 5. 为什么源码里几乎搜不到 `dsh.profile.bundles`？

因为真正的 Profile manifest 是用户运行时文件，通常位于 `$DSH_HOME/profiles/<name>/package.json`，默认就是 `~/.dsh/profiles/<name>/package.json`，而不是作为固定文件大量提交在源码里。

仓库源码保存的是生成逻辑和模板。[`PROFILE_TEMPLATES`](../../../packages/boot/app-boot/src/profile.ts) 定义 `web` 和 `headless` 的初始 Bundle 列表，`initProfile()` 首次使用时把它写入 Profile 的 `package.json`，`loadProfile()` 再从 manifest 读出它。

所以要看真实结果，应该先运行一个 Profile，再查看生成的文件或运行：

```sh
dsh --profile web --dump-config
```

## 6. `@deepseek-ai/dsh-web-app` 和 `@deepseek-ai/dsh-headless` 有什么区别？

它们都是叠在 `@deepseek-ai/dsh-base` 上的 Bundle。

`dsh-web-app` 增加 HTTP/API 和浏览器应用，目标是持续运行、让用户通过 Web 界面交互。

`dsh-headless` 增加一次性任务运行器，不带 Web、图形或 TUI 界面。它接收任务、运行、输出并退出，所以叫 Headless，也就是“没有面向人的界面”。

## 7. 所以 Headless 就是 CLI 吗？

在当前 dsh 产品里，Headless 通过 CLI 启动和交互，因此可以说它是 dsh 的一次性 CLI 运行模式。

但两个词不完全等价。CLI 描述输入和启动方式；Headless 描述程序没有图形、Web 或 TUI 人机界面。CLI 命令也可以启动一个有 Web 界面的服务。

## 8. Profile patch 与 Home patch 分别是什么？

Profile patch 是 `$DSH_HOME/profiles/<name>/cordis.patch.yml`，只属于并影响这个具名 Profile。

Home patch 是 `$DSH_HOME/cordis.patch.yml`，属于整个 Harness home，对这个 home 中启动的所有 Profile 生效。

应用顺序中 Home patch 在 Profile patch 之后，因此二者修改同一 `id` 和同一字段时，Home patch 生效；它们修改不同 id 时，两边的修改都会保留。

## 9. 既然最后还有 Home patch 和 `--patch`，为什么不只监听最后一层？

因为每一层通常只修改少数 `id`，最后一层不是一份完整配置，也不会替换整棵树。

Profile patch 和 Home patch 是两份彼此独立、运行中都可能变化的用户文件，所以都要监听。`--patch` 是启动时读取的临时 overlay，会固定保留在它们上方，但不被热监听。

任何被监听文件变化后，dsh 都重新组合 Bundle、最新 Profile patch、最新 Home patch 和启动时 overlay。这样删除一个高层修改时，较低层被遮住的配置才能恢复。

## 10. 之前为什么感觉最后一层会覆盖一切？

因为三个教学实验的各层都只使用了一个 `id`：`learning-observer`。每一层都命中同一条配置项，视觉上自然只剩最后一次写入的配置。

真实配置树有很多 id。正确的观察方式不是找“整棵树的最后一层”，而是对每个 id 找“最后一次命中它的 patch”。

另外，同一 id 被 patch 且 patch 提供 `config` 时，`config` 整个对象会被替换，不会深度合并。这个局部的整值替换也容易被误解成整棵树被替换。

## 11. 所以现在应该存在三个目录吗？

概念上可以分成三个位置：dsh 安装、Harness home 根目录、具体 Profile 目录。

物理层级上只有两个根：dsh 安装的依赖树和 `$DSH_HOME`。`profiles` 位于 `$DSH_HOME` 内，具体 Profile 又位于 `$DSH_HOME/profiles/<name>`。

```text
dsh 安装的依赖树/

$DSH_HOME/
├── cordis.patch.yml
└── profiles/
    └── <name>/
        ├── package.json
        ├── cordis.patch.yml
        └── node_modules/
```

## 12. dsh 安装中的官方 Bundle 只是 Bundle 级别的吗？一般安装在哪里？

`@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app` 和 `@deepseek-ai/dsh-headless` 这些包各自是官方 Bundle 包；但整个 dsh 安装还包含 CLI、插件包和运行库，并不只有 Bundle。

它们没有跨包管理器固定不变的绝对目录。可以把“dsh 安装目录”理解为当前 `@deepseek-ai/dsh` 所在的 Node 依赖树：全局 npm 安装、本地项目安装和 pnpm 工作区的物理路径都会不同。

在本仓库中，源码位于 `packages/bundle/*`，`apps/cli/node_modules/@deepseek-ai/` 下是 pnpm 创建的工作区链接。正式发布安装后，它们通常表现为 `@deepseek-ai/dsh` 的依赖。

还要注意，一个 npm 包可以同时包含 Bundle patch 和被该 patch 挂载的运行时代码。所谓“Bundle 包”是在描述它通过 `dsh.bundle.patch` 提供配置层，不代表包里只能放 YAML。

## 13. 为什么官方 Bundle 和 Profile 安装的 Bundle 不放在同一目录？

因为它们有不同的所有者、版本关系和作用范围。

官方 Bundle 由发行版拥有，必须和当前 dsh CLI 保持版本一致，所以跟随 dsh 安装和升级。外部 Bundle 由用户拥有，不同 Profile 可以选择不同包或不同版本，并且 dsh 升级时不应删除它们。

分开放置还能避免四类问题：不同 Profile 互相污染、修改程序安装目录需要额外权限、升级覆盖用户包、每个 Profile 复制一套官方核心依赖造成版本漂移或多份 Cordis 实例。

dsh 解析 Bundle 时先查安装依赖树，再查当前 Profile。因此内置 Bundle 保持可信且版本对齐，外部 Bundle 仍可按 Profile 隔离。

## 14. `dependencies` 和 `dsh.profile.bundles` 为什么都要有？

`dependencies` 是给包管理器看的，表示这个 Profile 需要安装哪些 npm 包。

`dsh.profile.bundles` 是给 dsh 启动器看的，表示哪些已安装包应作为配置层应用，以及应用顺序。

“已经安装”不等于“已经启用”。一个外部 Bundle 通常需要同时出现在 `dependencies` 和 `dsh.profile.bundles` 中。

## 15. `--dump-config` 和正常启动有什么区别？

`--dump-config` 读取并组合相同的配置层，但只打印最终配置树及来源，不执行配置项对应的插件。

正常启动会把最终配置树交给 Cordis Loader。Loader 按配置项的 `name` 解析插件模块，并把最终 `config` 传给插件的 `apply()`。

因此排查 Profile、Bundle 和 patch 时，先用 `--dump-config` 看“最终要挂载什么”，再启动程序看插件运行行为，通常最清晰。
